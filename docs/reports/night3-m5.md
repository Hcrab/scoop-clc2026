## Integration correction

A clean-reset run exposed a capacity check that refitted cohorts when opening Orders, leaving the screen at **Calculating** beyond the old 20-second assertion. Existing-plan capacity checks now use each saved order's already contextualized adjustment for order summaries, dashboard projections and approval. This keeps verification attached to the reviewed calculation. It does not alter forecast fitting, cohort detection, service targets, buffers or order quantities. Standalone capacity checks still fit when no saved factors are supplied.

`test_saved_capacity_factors_preserve_projection_without_refit_or_double_context` verifies equality of the full projection and fails if a refit or second context application is attempted. The API order-group test verifies that the actual stored adjustment reaches the check. **57 focused tests pass**, `reports/m5-orders-tests.txt`.

After restarting the API, the first order-summary request takes **2,104 ms** and reports the same **2,195 cases / 61.3045565055 of 66 pallets** as the direction preview (`reports/m5-capacity-timing.json`, `m5-capacity-python.txt`).

The expanded suite also exposed a Reset synchronization error in streaming chat: its activity lease was entered in the stream thread and released in the assistant thread, so resetting the `ContextVar` raised before decrementing activity. The reserved lease now enters and exits inside the same explicit context, and the stream finishes only after release. Success and rollback tests both check zero remaining activity and an immediate planning-reset lease. No paid model call is needed for these checks.

The first complete suite had **283 passed / 4 setup errors** because this host denied access to its global pytest temporary directory. The rerun uses a fresh, verified directory under ignored `.codex/pytest/`, following the existing workspace workaround, and treats unhandled thread warnings as errors. It does not change the global directory's permissions.

The final time-profile review reproduced **100.8403% fill at 22:00** on 27 July: all 9,898 daily units had shipped, but the uniform background still assigned some requests after dispatch close. Background requests now finish at **22:00**, retaining the 90% daytime / 10% background mix and nonzero overnight requests. Every dispatch-CDF point is tested against the request CDF, so cumulative shipments cannot imply fill above 100%. The same raw day now gives **100%**, with no clipped displayed value (`reports/m5-late-fill-before-python.txt`, `m5-late-fill-after-python.txt`). Daily simulation totals, policy settings and results stay unchanged. Cache version is `same-cold-store-play-v7`.
